# Boss and workers

You set up a project for a way of working: one long interactive **boss** session, on the strongest model, is the only session the person talks to. It picks the work, writes the briefs, starts **workers** (headless `claude -p` sessions on cheaper models) and decides what a worker would otherwise ask the person. The person hears from the boss only about what truly needs them.

You write the launchers, the rules and the state file, and help set up accounts. You never start the boss or real workers yourself, never log in to an account, and never turn on paid extras (usage credits, extra usage): those are the person's.

Project specifics come from `.claude/boss-workers.md` (Step P). This file stays general.

Supporting files, read them when a step points to them:
- `${CLAUDE_SKILL_DIR}/reference/profile-format.md`: the profile's settings, defaults and a fictional example.
- `${CLAUDE_SKILL_DIR}/reference/operating-rules.md`: the rules the boss and workers follow. The one copy: the boss reads it from the installed skill at every start, and projects never copy it.
- `${CLAUDE_SKILL_DIR}/reference/accounts.md`: the machine file of named accounts, a second account in its own config folder, the sign-in check, two stored logins in one folder, and the switch procedure.
- `${CLAUDE_SKILL_DIR}/reference/template/`: `boss` and `run-worker`, with `@PLACEHOLDERS@` (listed in `profile-format.md`).

## Step C: Context check (first, before anything costly)

Before Step P's heavier work, and before any write, run the check in `${CLAUDE_SKILL_DIR}/reference/context-check.md`. It decides whether this conversation is the right place to run the skill. On **fresh session** or **wait**, stop there and give the user what the check says. For this skill:
- **Moving target (5) and sequence (7) weigh most:** other sessions may be running in the project. Changing a launcher they use mid-run is safe (scripts are read at start), but the boss must not start while another session still orchestrates: say so in the hand-off.
- Authorship (2) and anchoring (4) don't apply. A long conversation (3) that discussed the setup is an advantage.

## Step P: Load the profile

1. Read `.claude/boss-workers.md` if it exists.
2. Otherwise discover: the agent-instructions file (CLAUDE.md or AGENTS.md), any existing launcher scripts for headless sessions (grep for `claude -p`), handoff or state files, where work happens (the root, or sub-folders such as `apps/*` or worktrees), the project's push and commit rules, other config folders under `~` that hold a Claude login (`.claude-*`), and the machine file of accounts (`~/.config/boss-workers/accounts`). Tell the user what you found and offer a starter profile (`profile-format.md`). Ask only what can't be found: each account's name (the person's own word, never a number) and address, if the machine file lacks them.

## Step 1 (check mode, or before setup): what's there

Report, without changing anything:
1. Launchers: do the profile's `boss` and `worker` paths exist, and do they pass `--model` and the account's config folder?
2. Accounts: is every account in the machine file, with its name, address and folder? Does `boss --check-accounts` say `ok` for each, with no folder holding two stored logins? Does `claude -p "/usage"` answer with limits? Do the logins stay apart (`accounts.md`, "Proving the logins are separate")? A launcher or profile from setup 0.6 or earlier names accounts with their folders: a finding, with the move in `profile-format.md`, "Moving from the old form".
3. Rules: does the boss launcher find the installed `operating-rules.md`, does the project's rules doc hold only the project's own rules (a full copy of the general rules is a finding: Step 2.2 cuts it down), and does the agent-instructions file point to both and to the state file? Does the version in the boss's state match the installed plugin's?
4. Sub-agent models: list the project's and installed plugins' agents without a `model:` line. They inherit the worker's model, which is usually right; say which would change if `CLAUDE_CODE_SUBAGENT_MODEL` were set, and recommend not setting it unless every reviewer names its model.
5. **Sandbox:** is Claude Code's sandbox on (`"sandbox": { "enabled": true }` in the user, project or local settings)? The boss starts workers from its own shell, so a worker runs inside the boss's sandbox (it nests), on top of its own. Say what workers typically lose there: `git worktree add` into paths the sandbox denies, `gh`, package installs and anything else that needs the network or paths outside the allow lists, and claude.ai connectors. Record both facts in the profile (`sandboxed`, and `workers_in`: does a worker change the boss's own repository, or other repositories under its folder that the root ignores?) and name the arrangement from `operating-rules.md`, "Under a sandbox": with the sandbox on and workers in the boss's own repository, standing clones the person makes once, one per parallel worker, never worktrees of it; with workers in nested repositories, those repositories and their worktrees; with the sandbox off, say plainly that nothing confines a worker but its rules and hooks. Never recommend excluding the worker launcher from the sandbox. Also: steps the sandbox blocks left to the boss's sandbox-excluded commands or to the person. Say also: a worker can't start its own sandbox inside the boss's, so the launcher starts it with its own off and the boss's sandbox alone confines it (`operating-rules.md`, "Under a sandbox"); and a session started inside the sandbox can't list or message other sessions unless the sandbox allows connections to the sessions' socket folder, so workers' questions arrive by handoff only until the person adds that folder to the sandbox's `network.allowUnixSockets` (offer the exact settings line; it's their decision). Standing worktrees need the project's install run in each by the person, or the commit gate fails there. Never turn the boss's sandbox off or widen it yourself; that's the person's choice.
6. **Hooks and registries:** does the project have a handoff or stale-state hook with a list of files to watch, a shell-lint list, build-tool inputs, or a generated list of ignored files? The new scripts, the state file and the `.claude-runs/` ignore line must be registered wherever the project registers such things.

In `check` mode, stop here with the report and the fixes.

## Step 2: Write the setup

Show every file before writing it; never overwrite a file the person changed without showing the diff.
1. **Profile:** write `.claude/boss-workers.md` if missing.
2. **The project's rules doc:** write the profile's `rules_doc` as a short file: one line saying the general rules are this skill's `operating-rules.md`, read from the installed skill at every start, and then only what is this project's own (its devices, checks, people, anything the general rules leave open). Never copy `operating-rules.md` into the project: a copy drifts from the other projects'. **A project set up before setup 0.6.0 has a full copy:** show the person which of its lines are general (now in `operating-rules.md`) and which are the project's own, move any general line the skill lacks into the skill (`operating-rules.md`, "Keeping the rules the same across projects"), and cut the doc down to the pointer and the project's own lines.
3. **Launchers:** copy `template/boss` and `template/run-worker` to the profile's paths (a file, or a folder per tool if that's the project's layout), replace every `@PLACEHOLDER@` from the profile (every occurrence on each line), `chmod +x`, and syntax-check them (`bash -n`). They find the project root with git, so any depth works. The worker launcher refuses the root itself: the boss works there (state commits, merges), so workers use sub-folders or worktrees. If the project already has a worker launcher, add the options and the root guard to it instead, keeping its own rules, and say so.
4. **Ignore and register:** add `.claude-runs/` to `.gitignore`, and register the new scripts, the state file and the ignore line wherever Step 1 found the project registers them (lint lists, build inputs, generated ignore lists, a handoff hook's file list).
5. **State file:** don't write it. The boss builds it on its first start from the project's handoffs (the boss launcher's opening prompt says how), so its first picture of the project is its own.
6. **Agent instructions:** add a short section to CLAUDE.md or AGENTS.md: the boss is the only session the person talks to; workers start through the launcher; where the rules doc and the state file are.
7. **Accounts:** write the machine file (`accounts.md`) after the person confirms each name and address; it's shared by every project on the machine, so add to it, never drop another project's line. For each non-default account, follow `accounts.md`: create its config folder with links to the shared settings, prove a fresh folder starts logged out, then give the person the sign-in command, to run at the machine. After they say it's done, run `boss --check-accounts` and `/usage` for each.
8. **Test:** run one throwaway worker through `run-worker` on each account with the cheapest model (with `BOSS_WORKERS_ACCOUNT` set, as the boss would; on the other account through `--account`, which warns), in a scratch folder the launcher accepts, briefed to change nothing outside its scratch folder, print `$CLAUDE_CONFIG_DIR`, run one shell command that must work (`pwd`) and, if the sandbox is on, one that must fail (`touch` a file in the home folder), report both results, run the project's gate once if the folder is a real worktree, and list the sessions it can see (ListAgents). Its printed config folder must be the account asked for, on every account, started the way the boss will be (including from a boss on a non-default account). A worker whose `pwd` fails has no shell: stop and fix the launcher before anything else. Say for each account whether its workers can see the boss, since a worker that can't leaves its questions in its handoff. Check that the root is refused, an unknown account is refused with the list of names and addresses, and the boss launcher without a terminal stops with the same list. Delete the scratch folder. If the sandbox is on, run the test the way the boss will (from the session's shell), so the worker meets the same limits.
9. **Commit** if the profile's `commit` is on (default on; one commit, the project's trailers), after the project's own gate passes. Push only if `push` is on, and push only this commit: if other commits wait to be pushed on the same branch, say so and give the person the command to push this one by its hash.

## Hand off

Reply with: the files written; what workers can't do under the sandbox, if it's on, and who does those steps; the accounts, each by name and address, and whether each was proven; how to start the boss (the exact command with `--account <name>`, and which account first, given each account's usage now); how a switch works (`accounts.md`); what to close first (any session still orchestrating; others wind down at a clean point and the boss takes over their work); and what the person still has to do. Never claim an account works until its `/usage` answered.
